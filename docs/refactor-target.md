# 通行证重构目标：组织、任职、权限与换届

本文定义重构完成后通行证应具备的能力、必须遵守的权限边界，以及需要退出运行系统的旧机制。它是目标规格，不是实施步骤，也不表示文中能力已经实现。

依据为 2026-10-19 的线上 Keycloak `master` realm 核对结果、[权限架构图](https://s3.bitnp.net/test/Keycloak-%E6%9D%83%E9%99%90%E6%9E%B6%E6%9E%84%E5%9B%BE.svg)、内部《Keycloak-身份与权限架构-实施说明.md》，以及本轮已确认的产品要求。文档不收录线上真实人员名单、凭据或客户端密钥。

## 已确认的产品边界

- Keycloak 保存账户、组织归属、任职、角色及组合关系，是身份与权限的唯一事实来源。
- 部门管理员只管理本部门成员和邀请。部门内部不增加另一套可细分、可委托的管理权限。
- 系统管理员维护组织配置、任职和经明确批准的个人特殊系统授权。
- 新成员使用邀请链接，按链接选项进入 Keycloak 注册，再加入目标群组。不预注册账户，不以学号设置初始密码。
- 通行证保留显式“纳入”和“取消纳入”。准备新届时默认纳入新群组；普通资料保存不改变纳入状态，纳入也不授予角色。
- 换届围绕 Keycloak 的组织组、成员身份映射和个人任职完成，旧本地委派授权不再转移。

本文编写时，本地 Keycloak 已具备新模型的开发数据，通行证业务代码尚使用旧权限和换届机制。目标验收包含业务适配，不能只以测试数据同步作为完成依据。

## 通行证的定位

`accounts.bitnp.net` 提供成员自助服务，以及组织、任职、邀请和换届的日常管理入口。`login.bitnp.net` 继续承担统一认证和原生账户安全流程。其他业务应用仍可直接对接 Keycloak，不需要先获得通行证本地会话。

通行证应把常用业务操作组织成容易理解的页面：查看本人身份与权限、维护部门成员、发送邀请、安排任职、确认换届影响。需要理解 Keycloak 底层配置的操作，如修改客户端、角色组合、scope 或 mapper，仍由 Keycloak 管理控制台承担。

通行证不自建注册表单、密码验证器、认证器管理协议或通用角色编辑器。已有的个人资料和账户安全能力继续复用 Keycloak。

## 身份与权限模型

### 必须分清的概念

**组织归属**由 Keycloak 群组成员关系表示，包括届别和所属部门。历史组织关系可以保留，但历史成员不因此成为现任。

**成员身份与职务**由 `position-*` 表示。普通成员身份通过部门组取得；主席、分管副主席、部门负责人和顾问等任职直接分配给个人。同一人可以兼任多个职务，同一职务可以有多名任职者。

**功能权限**由 `permission-*` 表示。应用根据有效功能权限判断是否允许访问或管理，不能把职务名称、所在页面或显示标签直接当成授权。

**现任标记**为 `bitnp-active`。它说明当前成员身份，不等于部门管理员或系统管理员。

**客户端角色与输出字段**服务于具体应用。scope 和 mapper 决定已拥有的角色如何进入令牌，不授予职务，也不创造权限。

**纳入通行证**表示通行证为一个已有群组提供门户功能和配置。它不改变 Keycloak 的组织归属、角色映射或认证状态。

关系方向如下，反向不成立：

```text
组织群组 / 个人任职
  → position-* 成员身份或职务
  → permission-* 功能权限
  → 必要的原生角色、客户端角色
  → 按客户端 scope / mapper 输出
```

拥有部门 `access` 不等于属于该部门。授予某部门职务也不自动补加该部门群组。两者不一致时，页面应分别显示，不能猜测人员归属并自动修正。

### 部门与组织结构

当前四个业务部门在模型中平级：

- `techdept`：技术部。
- `clinic`：电脑诊所。
- `digimedia`：数字媒体中心。
- `techsvc`：技术保障中心。

2026 年的组织映射为：

```text
/bitnp/active-2026                  → bitnp-active
  /2026-techdept                   → position-techdept-member
  /2026-clinic                     → position-clinic-member
  /2026-digimedia                  → position-digimedia-member
  /2026-techsvc                    → position-techsvc-member
  /2026-master                     → 无直接角色
  /2026-management                 → 无直接角色
```

`master`、`management` 群组保留组织表达作用，不能因其名称被当作系统管理员或所有部门管理员。旧 `orgdept` 等历史群组保留所需的成员历史，但不继续作为现行第五个业务部门。

群组 UUID 是操作和邀请绑定的对象标识。名称、显示名、年份和路径用于说明组织结构，不应通过宽泛字符串匹配授予权限。当前届部门归属必须能从受支持的 Keycloak 组织结构明确识别；未知或存在冲突的群组不能默认视作可管理部门。

### 必须支持的角色组合

当前业务模型包含 20 个 `position-*`、9 个 `permission-*`，另保留 `bitnp-active`。通行证读取并使用 Keycloak 组合关系，不维护可独立修改的第二份权限继承表。

部门功能权限：

- `permission-techdept-admin` 包含 `permission-techdept-access`。
- `permission-clinic-admin` 包含 `permission-clinic-access`。
- `permission-digimedia-admin` 包含 `permission-digimedia-access`。
- `permission-techsvc-admin` 包含 `permission-techsvc-access` 和 `permission-system-admin`。
- 四个 `permission-<department>-access` 为普通功能访问权限。
- `permission-system-admin` 包含原生 realm `admin` 和 `rustfs-console` 的客户端角色 `consoleAdmin`。

协会任职：

- `position-association-chair` 包含四个部门的管理权限，经技术保障中心管理权限获得系统权限。
- `position-association-vice-chair` 是共同身份，不直接包含功能权限。
- `position-association-vice-chair-techdept` 包含共同副主席身份和技术部管理权限。
- `position-association-vice-chair-clinic` 包含共同副主席身份和电脑诊所管理权限。
- `position-association-vice-chair-digimedia` 包含共同副主席身份和数字媒体中心管理权限。

部门身份与任职：

- 四个 `position-<department>-member` 分别包含对应部门的 `access`。
- 技术部、电脑诊所、数字媒体中心各自的 `head`、`deputy-head`、`advisor` 职务分别包含本部门 `admin`。
- `position-techsvc-director`、`position-techsvc-deputy-director` 包含技术保障中心 `admin`，因此包含系统权限。

技术部分管副主席、技术部部长和顾问，不因这些职务获得系统权限。普通技术保障中心成员也没有系统权限。个人另有明确特殊授权时，应显示为独立来源。

不能创建包含所有 `position-*` 的“分类角色”。Keycloak 的组合角色会授予其子角色，不能用它模拟文件夹。权限角色也不能反向包含行政职务。

## 操作者能够做什么

### 普通成员与未登录访客

未登录访客可以访问公开首页、帮助与有效邀请入口。查看个人资料、加入群组和管理操作都需要相应身份；公开入口不能泄漏完整成员目录、管理名单或邀请管理信息。

已登录成员可以查看和维护自己的账户资料，查看自己的组织关系、任职与有效权限，使用邀请加入允许加入的普通成员组，并通过 Keycloak 处理密码、通行密钥、其他认证器和登录会话。

只有 `permission-<department>-access`、`bitnp-active` 或某个普通群组成员身份，都不能管理该部门成员。

### 管理层与部门管理员

持有任一部门 `permission-<department>-admin` 或 `permission-system-admin` 的用户即可进入管理工作台，查找用户并维护所有人的成员业务资料（目前为 QQ），无需额外角色。部门管理层仍不能修改其他部门的组织关系，或修改他人的姓名、邮箱、验证状态和账户启停状态。

持有有效 `permission-<department>-admin` 的用户，可以管理通行证开放给该部门的成员与邀请，包括单人操作和已有的批量成员操作。部门范围由对应组织关系决定，不因操作者本人加入多个群组而扩大。

部门管理员不能任命职务、授予个人系统权限、修改角色组合、管理其他部门、修改站点设置，或通过群组配置给自己增加管理范围。部门内部不提供“再分配管理员”“委托给另一个群组”等入口。

对技术保障中心管理者，页面必须如实显示：其线上有效权限中还包含系统权限。这来自现有组合关系，不能为了统一页面称呼而忽略。

历史组织关系的保留不应自动重新开放历史邀请，也不能使历史群组重新携带当前成员权限。涉及历史成员的管理范围应在产品中明确表达，不能通过当前部门权限和同名路径无差别扩大。

### 系统管理员

通行证以有效 `permission-system-admin` 作为系统管理权限，包括通过主席、技术保障中心任职继承，以及经批准直接授予个人的情况。

系统管理员可以维护门户群组配置、各部门成员与邀请、任职、个人特殊系统授权、换届和站点设置，并查看相应任务与操作记录。

仅拥有 Keycloak 原生 `admin` 的账户，不反向获得 `permission-system-admin`。它仍可按 Keycloak 自身授权使用管理控制台，但不被通行证自动认定为新模型的系统管理员。遗留维护账户、服务账户及其原生授权不属于换届清理范围。

管理员列表必须包含通过组合关系取得权限的有效持有人，不能只查询直接持有某一个角色的用户。已停用账户也不能被计为可用的管理入口。

### 服务账户

`bitnp-passport-service` 是通行证访问 Keycloak 的技术身份。它能调用某个接口，不表示当前用户可以执行这个操作；服务端始终依据操作者的业务权限判断。

当前服务账户已有 `master-realm` 的 `manage-users`、`view-realm`、`view-clients`、`query-clients`，并限制角色输出范围。新增任职或角色映射能力需要满足对应 Admin API 的实际授权要求，不能把只读角色解释成写权限，也不能为省事直接授予完整 `admin`。

## 重构后应具备的功能

### 本人的身份与权限

个人页面应分别显示组织归属、现任状态、个人任职、功能权限和可管理部门。普通用户使用业务名称，角色标识和具体来源可在详情中查看。

每项权限应能说明当前来源，例如“技术部副部长 → 技术部管理”“技术保障中心副主任 → 系统管理”或“个人特殊系统授权”。同一权限存在多个来源时应同时展示，不能只保留第一条来源。

页面应区分直接组织成员关系、父群组继承、个人直接任职和个人特殊授权。用户不应看到旧“群组委托”被包装成新职务。

权限展示与服务端执行使用同一业务定义。页面隐藏按钮是交互处理，不能代替接口鉴权。令牌中的旧角色也不能让已经撤职的用户继续提交管理操作。

### 用户目录与任职管理

管理工作台提供成员目录与业务资料维护，并连接我管理的群组、任务和操作记录；系统设置独立提供群组配置、账户控制、任职授权、换届和站点设置。系统管理员也通过管理工作台维护成员业务资料，成员详情另有系统管理员专用的“账户与授权”入口。

管理工作台与系统设置保留独立按钮，按权限显示。群组管理、任务和操作记录仅向管理层开放，页面与接口均校验管理层身份；普通用户的站点导航只提供我的账户和帮助。

管理层可以查找已有 Keycloak 用户、查看基本资料并维护成员业务资料。系统管理员另外可以查看其归属、任职、直接特殊授权和有效权限，并维护个人职务。用户识别使用稳定 UUID；用户名、姓名和邮箱仅供查找与显示。存在同名、多重匹配或账户停用时，不能自动猜测任职对象。

任职操作应满足：

- 可为同一个人设置多个互不覆盖的职务。
- 同一个职务允许多人持有，也允许暂时空缺。
- 普通成员身份来自组织组，不能把任职面板变成给个人随意发放 `position-*-member` 的工具。
- 分管副主席分配具体分管职务，共同副主席身份按组合继承，不要求管理员重复勾选。
- 撤销一项任职仅撤销该项个人角色映射，其他职务、组织成员关系和独立特殊授权保持原状。
- 操作前后能够看出有效权限变化。撤职后仍有相同权限时，应说明剩余来源，不能显示“系统权限已完全撤销”。

个人特殊系统授权应是明确、独立的操作，不能混在“保存个人资料”“加入部门”或“任职继任”中。它直接作用于 Keycloak 的 `permission-system-admin`，不产生通行证本地管理员记录。

通行证不开放任意 `permission-*` 直接发放，不编辑角色组合，也不创建用户自定义职务体系。普通授权仍通过已定义的职务与组映射表达，个人系统特批作为已确认的例外。

### 群组与门户纳入

Keycloak 中存在的群组、已纳入通行证的群组、操作者能够管理的群组，是三个不同状态。管理配置页可以展示它们的区别，日常成员管理页不能把所有 Keycloak 群组都显示成可管理对象。

“纳入通行证”“取消纳入”必须是明确操作。保存名称、显示名或说明不改变纳入状态。取消纳入不删除 Keycloak 群组、成员、任职或凭据，但应关闭该组门户邀请，并使已有链接不能继续加入。

门户可以保存群组显示名、说明、纳入状态与邀请开关。这些是门户配置，不是另一套组织权限来源。群组重命名不导致邀请、任务和历史记录改绑到另一个对象。

成员与邀请操作按固定的部门群组和角色映射执行，检查操作者的管理范围与邀请有效性，不在每次操作前重新扫描群组的角色效果。批量接口与后台任务使用相同的授权规则。

### 邀请与 Keycloak 注册

邀请继续绑定一个明确的目标群组，保留有效期、撤销、备注和“允许注册”选项。部门管理员在自己的范围内创建与维护邀请；系统管理员可以跨部门管理。

没有账户的人，在链接允许注册且 realm 允许注册时，进入 Keycloak 原生注册页面，自行填写用户名、密码和个人信息。已有账户的人直接登录。认证完成后回到原邀请，明确显示目标群组和加入结果；已是成员时不重复报错。

通行证不能采集新用户密码，不能创建空白账户等待认领，也不能要求用户先去别处注册再手工寻找原链接。注册取消、认证失败或加入失败时，应保留可理解的返回与重试入口。

链接的“允许注册”只决定该邀请是否提供注册入口，不等于为整个 realm 建立“只有持邀请才能注册”的限制。realm 和其他客户端的注册策略仍由 Keycloak 决定。

加入时必须重新检查登录身份、链接有效性、群组纳入状态、邀请开关和目标组的授权边界。打开过有效页面，不代表稍后仍可加入。撤销、到期、取消纳入和换届关闭的链接都不能继续使用。

未受换届或群组停用影响的既有有效链接，应保留其目标和效力。旧届链接不能在用户不知情时自动改为新届链接。持有邀请仅允许加入对应的普通成员组，不授予职务或个人特殊系统权限。

### 批量操作、任务与操作记录

现有批量成员管理有实际用途，应继续提供操作预览、执行结果、逐项失败说明、重试和取消。任务由后台执行时，要按执行时的操作者权限检查，不能沿用创建任务时无限期有效的管理资格。

任务的成功、失败、取消和结果未知必须如实表达。外部调用成功但本地未记录的情况，不能直接当作失败并无条件重复执行。重试应以当前 Keycloak 状态为准，避免重复副作用。

成员、邀请、任职、特殊授权与换届等管理变更保留必要的操作记录：操作者、时间、目标、变更内容和结果。部门管理员不能借任务或记录接口查看其他部门的敏感信息。

这些记录用于解释实际业务操作，不建立快照签名、证据链、哈希凭证、双向对账数据库或通用工作流平台。

## 新换届功能的完成态

### 换届操作表达的内容

换届是“新届组织接替当前组织，并按明确名单调整任职”。它应覆盖现任标记、部门成员身份映射、个人职务和相关邀请的变化。

操作者应能明确表达哪些任职结束、哪些人继续任职、哪些人新任或兼任，以及哪些邀请随旧届结束关闭。系统不能默认复制上一届所有成员、管理员或个人特殊授权。

新届群组可以提前准备，但准备新届结构不能提前赋予本届现任标记、当前成员权限或管理权限。正在准备的结构也不能把旧届有效组织关系自动删除。

准备组织使用固定的 `/bitnp/active-年份/年份-部门` 结构，新建群组默认纳入门户。重复准备只补齐缺少的组织与门户配置，不重置已有邀请设置、显示名或手动取消纳入状态。

### Keycloak 中应成立的结果

正常完成换届后：

- 有唯一明确的当前届组织根组，由 `bitnp-active` 的组织映射体现；历史根组不再授予现任标记。
- 新届四个部门组具有对应的 `position-<department>-member` 映射，旧届组不再因旧映射提供当前成员身份及其功能权限。
- 历史届别群组及其必要成员关系仍然可查。一个人在多个年份出现，不应因为旧组仍存在而继续得到当前成员权限。
- 个人任职与确认后的任职安排一致，支持留任、离任、兼任、多名任职者和空缺。
- 个人直接的特殊系统授权独立保留，既不随职务撤销而误删，也不自动转给继任者。
- 原生管理账户、服务账户、无关客户端角色、认证配置、用户凭据和客户端密钥保持原有用途。
- 受影响的旧届邀请明确失效；新届邀请指向新届群组，不重用旧链接偷偷改变加入目标。

通行证不能只移动 `bitnp-active` 就声称完成换届。个人职务和部门组的成员身份映射是同一业务结果的一部分。

当前届由届别根组直接分配的 `bitnp-active` 确定，不另存本地状态。迁移后的群组结构和角色组合由我们统一维护，日常请求按此约定读取，不额外巡检根组数量、标记位置或复合角色来源。

个人直接拥有 `bitnp-active` 等模型外配置应作为单独来源展示。换届不能静默清空无关个人映射，也不能隐瞒这些映射使某人仍为现任的事实。

### 操作者应看到的结果与影响

确认换届之前，页面需要说明旧届与新届、成员身份映射的变化、任职变化、受影响的邀请，以及应保留的个人特殊授权。重点是实际对象和业务结果，不要求操作者阅读底层 JSON。

确认后提交到现有后台任务队列，任务页显示等待、执行、进度和逐项结果，离开页面不影响执行。全组织同时只有一个未结束的换届任务。后台开始执行时重新校验整份安排；等待中的任务可以取消，执行中的任务不能取消或直接重放。失败或中断后先核对已完成结果，再按当前状态重新预览。

任职引起的系统权限增减应突出显示。存在其他来源时，页面应说明撤销本项后仍保留什么权限。不能把“撤销某个职务”显示成“清空此人的所有管理能力”。

成员与任职名单不一致、找不到用户或用户已停用时，必须指出具体对象。系统不按姓名猜测账户、不自动补齐行政归属、不默默丢弃无法处理的条目。

### 失败、并发与安全边界

Keycloak 多个 Admin API 调用不具备跨请求事务。换届结果必须区分完成、未完成和需要继续处理的部分，不能宣称所有变化可以像单个数据库事务一样自动回滚。

部分失败后，已生效的组织或任职变化不能被本地状态遮蔽。页面应能说明哪些结果已确认、哪些失败、哪些需要重新核对，并基于实际状态继续处理，避免再次清空已正确授权的人。

换届与普通成员、任职管理发生并发时，不能无声覆盖别人已经完成的修改。执行时发现目标关系发生变化，应明确报告冲突；原先看到的预览不构成永久执行许可。

换届不得移除最后一位可用的有效系统管理员而使通行证失去管理入口。可用管理者按新权限模型计算，包含组合继承，不能把只有原生 `admin` 的维护账户或已停用账户计入。

预览和执行开始前都必须按整份安排校验最终管理权限。最终没有启用的真人系统管理员时，应在关闭邀请、调整任职或切换群组映射前拒绝操作；执行时仍保留逐项撤权保护。个人独立授予的原生 `admin` 不随换届撤销。

实现只需要承载这些实际业务结果和必要的失败恢复，不保留旧任期引擎，也不另造通用审批、分布式事务或执行凭证体系。

## 数据归属与必须保留的内容

### Keycloak 持有的事实

账户 UUID、用户名及个人资料、账户启停状态、密码与其他凭据、群组及成员关系、个人职务、特殊授权、角色组合、客户端及其密钥、scope 和 mapper，均由 Keycloak 持有。

通行证可以读取这些事实并提供经授权的修改入口。它不保存另一份可独立编辑的人员目录、有效权限清单、部门成员名单或任职现状。请求内计算和必要的短期缓存不能成为永久授权来源；权限读取失败时不能假定用户仍有管理权限。

### 通行证需要的持久数据

下列数据仍有独立业务用途：

- 门户会话、加密令牌及注销防重放状态。
- 群组在门户中的显示、说明、纳入状态和邀请开关。
- 邀请链接、目标群组、有效期、撤销状态和允许注册选项。
- 实际批量任务及逐项结果。
- 必要的操作历史及失败处理信息。
- 站点帮助链接和服务入口等门户设置。

操作记录原样保留当时的操作名、目标标识和详情。已退出的操作不保留专属标签、任期目标还原或旧配置展示；查看这些记录时仅显示原始操作名、标识和详情。操作历史不能反过来决定当前任职和权限。

### 数据与持久化约束

重构不能删除用户、密码、通行密钥、OTP、历史成员关系、客户端密钥或无关授权。取消门户纳入也不能触发这些删除。

不受业务状态变化影响的有效邀请和登录集成继续使用原对象。已有任务和操作记录继续保留，查询不依赖旧任期表，也不承担旧架构数据的转换或还原。

已经部署的数据库迁移历史保持有效，不能为清理代码重写历史迁移。后续结构变更使用现有迁移工具生成 SQL，并为迁移选择描述业务目的的名称；不手写迁移 SQL，不添加与变更无关的注释。

## 必须移除的旧机制

### 本地管理员与群组委派

最终运行系统不再依赖以下能力：

- `portal_admins` 维护的本地系统管理员身份。
- `group_delegations` 维护的个人或群组委派管理关系。
- “Keycloak 原生 `admin` 或本地管理员即通行证系统管理员”的混合判断。
- 通过管理层群组、历史委派或名字推断某人的管理范围。
- 部门管理员再次授予部门内细分权限或跨组管理权。

相关的旧管理员授予、委派增删接口、界面、类型和调用路径应退出运行代码。新的任职与个人特殊授权页面直接操作 Keycloak，不能继续写旧表作为“兼容”。

`scripts/grant.ts`、`admin:grant` 等本地授权入口不再作为初始化或应急管理办法。管理入口应来自 Keycloak 的明确授权；文档不能继续教用户向本地表补管理员。

### 旧任期与换届引擎

旧机制以 `terms`、`term_groups`、`departments` 及本地 `draft/current/archived` 状态维护年度事实。重构后的组织与换届不再由这些表决定。

需要退出的旧行为包括：

- 固定七类年度模板，把 `orgdept`、`master`、`management` 都按同类业务部门处理。
- 按本地任期状态选取当前届，或用本地任期关系补救 Keycloak 中不同的实际状态。
- `clinicCompatible` 等为了旧群组创建方式保留的双套规则。
- 依赖 `bitnp-pass-term`、`bitnp-pass-department` 本地记录关联才能识别现有组织。
- 只移动现任角色、复制或撤销本地委派，就宣布新任期已启用。
- 将旧 `creation`、`activation` JSON 计划及其状态机作为新换届的基础引擎。
- 把委派转移选项改名成任职转移，但仍按旧委派关系执行。

`backend/terms.ts`、`backend/terms/*`、旧任期页面与 `TermCreationPlan`、`TermActivationPlan` 等专属类型不应作为未使用的备用实现留在业务运行路径。旧表和枚举也不保留为空壳权限源；有价值的历史信息按业务历史保留。

`activeAffiliationGroup` 等旧属性不能决定当前届。已发现 `/bitnp` 的旧属性仍指向 `active-2019`，而实际现任映射在 2026 根组，这类遗留值不能被当作新模型的补充事实来源。

### 旧配置导入与角色名称

`scripts/import-legacy.ts`、随镜像分发的旧 `group_config.json` 和 `config:import` 不再承担新系统日常初始化、部门定义或权限恢复。确有历史保存价值的资料可以作为明确的历史材料，但不能继续存在可重新启用旧授权模型的生产入口。

以下旧角色字符串不再作为新通行证的鉴权常量或别名：`techdept-member`、`clinic-member`、`digimedia-member`、`techdept-admin`、`clinic-admin`、`digimedia-admin`、`system-admin`。线上已经按原角色 ID 改名为相应 `permission-*`，没有建立旧名兼容角色。

已移除的 `iam-admin` scope 或旧同名 client role 不恢复。原生 `admin`、`bitnp-active` 以及其他应用仍在使用的客户端角色不属于本节删除对象。

### 旧页面与耦合

旧“管理员”授予页、“群组委托”面板、旧“任期配置”表单及其专属接口退出产品。新页面围绕组织成员、任职、独立特殊授权与换届结果表达，不沿用旧字段迫使新概念适配。

群组列表、权限来源、任务查询、操作记录和导航不能继续依赖旧任期表或本地委派表。旧页面入口不能仅仅隐藏后继续允许接口修改旧状态。

这些删除不涉及正常的邀请、门户纳入、批量任务、会话和业务操作记录。不能为了清理旧换届而顺带删除仍有用途的功能。

## 代码层级应有的职责

重构应使一次操作能够沿着明确的业务路径完成：接口取得当前操作者和输入，业务层判断该操作与范围，Keycloak 访问层读写身份事实，门户持久化层保存门户自身状态。页面消费业务结果，不能重新计算一套权限。

权限判断集中表达“谁能对哪个部门或对象执行什么操作”。成员管理、邀请、任职和换届共享这些业务定义，不各自拼接本地管理员、群组成员、委派或角色字符串作为补丁。

组织识别负责群组与届别、部门的关系；任职管理负责个人任职与有效权限变化；邀请负责链接有效性与加入流程；换届负责一次组织交接应产生的结果。它们不通过通用 `settings` 对象互相暴露内部状态，也不各自保存一份当前届或当前权限。

Keycloak 访问层封装实际 Admin API 与 Account API 交互，并传递可诊断的外部错误。它不决定部门业务政策，也不因接口返回错误而退回本地授权。只为实际生产调用提供接口，不为测试暴露内部状态。

不需要通用权限规则引擎、插件注册表、策略 DSL、泛化换届工作流或为了连接这些机制而产生的中间层。模块划分应减少业务调用者需要理解的细节。

## 认证与外部应用契约

保留现有 OIDC 授权码、PKCE S256、state 和 nonce 校验，令牌签名、issuer、audience 与有效期校验，以及会话令牌加密、安全 Cookie、刷新与后端注销处理。不能因角色迁移降低这些约束。

管理写操作以执行时可确认的有效权限为准。不能信任浏览器提交的角色数组、未验证 JWT 或本地登录时固化的管理员布尔值。Keycloak 不可用时返回明确错误，不退回旧授权模型。

角色输出应遵守现有客户端配置：

- Realm 角色通常位于 `realm_access.roles`。
- 客户端角色通常位于 `resource_access.<client_id>.roles`。
- RustFS 的 `rustfs_policy` 只来自 `rustfs-console` 的角色映射，固定策略值仍为 `consoleAdmin`。
- scope / mapper 与角色输出范围决定具体 token 中包含哪些角色。拥有有效权限，不保证所有客户端的 token、ID token 或 UserInfo 都带有该字段。
- 不能假设 UserInfo 总能返回角色，也不能因缺少输出就再向用户直接授予一次权限。

通行证重构不重新定义其他业务应用的 `groups`、`memberof` 或 CAS 属性语义，不删除现有 `/auth` 路径兼容规则，也不顺便改变客户端密钥、注销协议或应用重定向地址。其他客户端需要适配已改名的角色时，应作为其集成契约处理，不能通过恢复旧通行证授权系统掩盖。

Keycloak 的完整架构迁移由外部完成。通行证直接使用迁移后的角色、组合关系和组织群组，不读取旧角色别名、旧任期属性或本地授权表，也不提供旧架构兼容或迁移入口。Keycloak 升级、LDAP 凭据迁移、CAS 插件替换和登录主题改造不由通行证处理。

## 目标验收场景

以下是应成立的业务结果，不是实施顺序。本地 [开发权限数据](../dev/README.md) 提供对应测试对象；验收不能只验证角色 JSON，还应覆盖通行证页面、接口和后台执行结果。

### 管理边界

- `member` 能查看本人身份及技术部访问权限，不能添加部门成员、维护邀请或任命职务。
- `manager` 作为技术部部长，能管理技术部成员与邀请，不能管理电脑诊所或任命新部长，也不显示系统管理权限。
- `vice-techdept-1` 具有技术部分管职务，管理范围与线上组合一致，不自动获得系统权限。
- `2026-techsvc-1` 仅获得普通技术保障中心访问权限，不能因为属于该组而成为系统管理员。
- `2026-master-1`、`2026-management-1` 不因群组名称获得管理权限。
- `chair-1` 及技术保障中心正副主任获得组合继承的系统权限，并出现在有效系统管理员列表。
- `legacy-admin` 仅拥有原生 `admin` 时，不被识别为新通行证系统管理员。
- 每个群组、职务和功能权限在测试数据中有多名有效持有人，列表、分页、修改与管理入口保护不能假设只有一名拥有者。

### 多来源与撤销

- `vice-techdept-special` 撤销分管职务后，其个人特殊系统授权仍然存在；不能把授权复制给下一位分管副主席。
- `multi-position` 撤销技术部副部长后，电脑诊所顾问及相应权限保持有效，页面说明剩余来源。
- `external-director` 的技术保障中心职务有效，但不被自动加入技术保障中心成员组。
- 撤职、撤销个人授权或变更群组映射后，原页面和已排队任务都不能继续凭旧管理状态越权执行。
- 实际移除最后一位可用系统管理员的操作被拒绝，计算包含继承权限且排除停用账户。

### 邀请、门户纳入与历史

- 无账户的受邀者能够使用 Keycloak 原生注册完成账户创建，并返回原邀请加入正确群组。
- 关闭注册链接选项后，不再由该邀请提供注册入口；已有账户仍按链接当前状态登录和加入。
- 链接到期、撤销、组邀请关闭或取消纳入后，已经打开页面的人也不能继续加入。
- 保存群组资料不自动纳入；取消纳入不删除 Keycloak 群组及成员。
- 管理员配置目录中的所有群组，不会因此全部出现在普通部门成员管理列表中。
- 历史成员如 `2025-techdept-1` 不因历史组保留而获得当前成员身份或部门访问权。

### 换届与持久化

- 换届后，当前根组、四个部门成员身份映射与个人任职均符合明确安排，历史组织关系仍可查。
- 个人特殊系统授权、服务账户和原生维护授权不被批量清空，也不自动转给新任职者。
- 旧届邀请按换届影响关闭，无关有效邀请保持原目标，新届链接不能被旧链接冒用。
- 外部请求中断或并发修改时，能够看到真实的部分结果和冲突，不把未完成交接显示为全部完成。
- 已有任务和操作记录仍可查询；已退出的操作只保留原始内容，不再还原旧任期或旧授权模型。
- 当前届只有 Keycloak 组织映射一个事实来源。旧本地 2026 草稿记录或指向 2019 的遗留属性都不能覆盖它。
